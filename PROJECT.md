# PROJECT.md — продуктовый документ StubGraph

## 1) Продукт в одном абзаце

StubGraph — инструмент для команд разработки, который помогает понимать кодовую базу через граф зависимостей файлов и запускать контекстные LLM-задачи по выбранным узлам графа. Продукт объединяет навигацию по проекту, анализ влияния изменений, поиск (включая семантический) и управляемое применение patch-изменений через асинхронный pipeline.

## 2) Целевая аудитория

- Backend/Fullstack разработчики, работающие с монорепо и legacy-кодом.
- Tech Lead/Architect, которым нужна быстрая оценка зависимости модулей и impact-анализ.
- Команды, внедряющие AI-assisted workflows, но требующие управляемости (очереди задач, история run, проверяемые патчи).

## 3) Ценность продукта

- Сокращает время на поиск связей между файлами.
- Даёт единый интерфейс для «понять код → сформулировать задачу → получить результат/patch».
- Снижает риск нецелевых изменений за счёт контекстных ограничений patch/индексации и истории запусков.

## 4) Ключевые пользовательские сценарии

1. **Подключить проект**
   - Создать проект по локальному пути или импортировать snapshot.
2. **Построить граф**
   - Запустить scan и получить/обновить зависимости.
3. **Найти нужный файл/участок**
   - Использовать структурный, текстовый или семантический поиск.
4. **Понять контекст**
   - Открыть контракт узла, зависимости файла, локальный подграф.
5. **Запустить LLM-задачу**
   - Выбрать режим `analyze|evolve|fix|impact`, контролировать параметры retrieval.
6. **Применить результат**
   - Просмотреть patch, применить изменения, повторно индексировать и обновить граф.

## 5) Scope (текущий, по фактам репозитория)

### In scope

- Multi-org модель с ролями (owner/admin/member/viewer).
- CRUD для проектов и файлов внутри проекта.
- Асинхронные background jobs через Redis + ARQ (scan/docs/import/run/mutation indexing).
- Сохранение run-истории и patch-данных.
- Frontend workspace: граф + редактор + боковые панели + командная палитра + docs modal.

### Out of scope / не подтверждено в коде

- Billing/платежи и self-service подписка (в моделях есть сущности планов/подписок, но UI/flow биллинга в текущем scope не подтверждён).
- Публичный SaaS-ready onboarding/tenant provisioning вне текущего auth/org API.

## 6) Функциональные блоки

### 6.1 Управление доступом и организациями

- Auth endpoints: bootstrap, register, login/logout, API keys.
- Org endpoints: list/create org, управление участниками.
- Контекст организации передаётся через `X-Org-ID` (frontend поддерживает хранение выбранного org).

### 6.2 Управление проектом и индексом

- Создание проекта по локальному `root_path`.
- Импорт проекта из archive snapshot через background task.
- Scan проекта в фоне, обновление графа и node metadata.

### 6.3 Граф и поиск

- Полный граф проекта с лимитом узлов.
- Локальный граф по центральному пути (`hops`, `max_nodes`, `max_edges`).
- Три канала поиска: node/semantic/text.

### 6.4 LLM-задачи и патчи

- Run task по файлу с выбором режима.
- Поддержка retrieval-стратегий:
  - agentic tool-based retrieval,
  - pack context,
  - graph-oriented constraints.
- Run history: список запусков, детали, patch, apply patch, delete run.

### 6.5 Документация проекта

- Генерация и чтение markdown docs по проекту.
- Отображение docs во frontend modal с переходами к файлам.

## 7) Нефункциональные требования (наблюдаемые)

- **Асинхронный runtime** в backend и queue boundary.
- **Валидация конфигурации** через `Settings` (строгие ограничения env-параметров).
- **Rate limiting** и middleware-цепочка для auth/session lifecycle.
- **CORS** настраивается через env.
- **Логирование и health endpoint** для runtime-наблюдаемости.

## 8) Метрики продукта (рекомендуемые)

> Ниже — продуктовые метрики как предложение, они не полностью реализованы как готовые dashboards в репозитории.

- Time-to-first-graph после создания проекта.
- Доля успешных scan/run/docs jobs.
- p50/p95 времени выполнения `tasks/run`.
- Доля run с применённым patch.
- Частота fallback с semantic search на text/структурный поиск.
- Ошибки auth/org-context (401/403) на API.

## 9) Риски и ограничения

- LLM-функции зависят от корректной конфигурации OpenAI и лимитов окружения.
- Качество графа и поиска зависит от полноты индексации (graph может быть stale до завершения scan).
- Потенциальное инфраструктурное расхождение: в compose указан `frontend/Dockerfile.prod`, в дереве репозитория виден `frontend/Dockerfile`.
