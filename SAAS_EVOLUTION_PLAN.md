# План эволюции StubGraph до масштабируемого SaaS (1 млн DAU)

Документ фиксирует результаты статического аудита репозитория и последовательный план миграции к полноценной SaaS‑архитектуре. План выстроен так, чтобы **каждый этап давал измеримый эффект** и не ломал базовые контракты сервиса.

## 1) Статический аудит текущего состояния (по коду)

### Хранение данных
- Используется **SQLite в локальном каталоге** пользователя; инициализация схемы производится при старте через `SQLModel.metadata.create_all(...)`. Это фиксируется в `backend/app/db.py` и `backend/app/main.py`.【F:backend/app/db.py†L1-L134】【F:backend/app/main.py†L1-L27】
- Используется **SQLite FTS5** для полнотекстового поиска (виртуальная таблица `filetext_fts`) в `backend/app/db.py`, что не совместимо с PostgreSQL без адаптации.【F:backend/app/db.py†L32-L58】

### Очередь/фоновые задачи
- Очередь фоновых задач реализована **in‑memory** через `ThreadPoolExecutor`, что не выдерживает рестарты/масштабирование. Состояние хранится в памяти процесса (`TaskQueue`).【F:backend/app/services/task_queue.py†L1-L112】
- Фоновые задачи используются для сканов/LLM‑задач через `task_queue.submit(...)` в сервисах `project_service` и `task_service`.【F:backend/app/services/project_service.py†L226-L240】【F:backend/app/services/task_service.py†L1304-L1312】

### Аутентификация/пользователи
- В текущих моделях отсутствуют сущности пользователей, организаций, ролей и подписок (`backend/app/models.py` содержит только Project/FileNode/AnalysisRun и т.д.).【F:backend/app/models.py†L1-L200】
- Роуты `backend/app/api/*.py` не содержат авторизации и контроля доступа на уровне пользователя/организации (проверки не обнаружены по коду).【F:backend/app/api/projects.py†L1-L125】【F:backend/app/api/tasks.py†L1-L123】

### Кэш и rate‑limit
- Redis/кэш/лимиты запросов отсутствуют в конфигурации и коде: нет клиента Redis, нет rate‑limit middleware. Конфигурация в `backend/app/config.py` не содержит параметров Redis/лимитов кроме LLM‑лимитов.【F:backend/app/config.py†L1-L171】

### Observability
- Логирование базовое (формат stdout), нет метрик/трассировок/корреляции запросов. Настроено только через `logging.py`.【F:backend/app/logging.py†L1-L46】

### Контейнеризация
- В репозитории отсутствуют Docker Compose/K8s манифесты, README содержит только локальные инструкции запуска через `uvicorn`/`npm` без контейнеров.【F:README.md†L47-L93】

## 2) Целевая архитектура (под 1 млн DAU)

- **PostgreSQL 16 + Alembic** (основная БД и миграции).
- **Redis** для кэша, rate‑limit, ephemeral sessions.
- **RabbitMQ** как надёжный брокер критичных задач (billing/auth/webhooks/heavy tasks).
- **Celery** для фоновых и периодических задач, отдельные worker‑пулы.
- **Объектное хранилище** (S3‑совместимое) для артефактов/патчей.
- **Kubernetes** (prod) + Docker Compose (dev/stage).
- **Observability**: Prometheus/Grafana + OpenTelemetry.

## 3) Поэтапный план эволюции (логический порядок)

Ниже — оптимальный порядок, где каждый этап **разблокирует** следующий. Для каждого этапа указана цель, действия и критерий готовности.

### Этап 0 — Контейнеризация и окружения (foundation)
**Цель:** получить воспроизводимые окружения, чтобы безопасно менять инфраструктуру.
1. Добавить `docker-compose.yml` (backend, frontend, postgres, redis, rabbitmq, worker).
2. Ввести `.env.example` и единые переменные окружения.
3. Разделить конфиги для dev/stage/prod (минимум: разные DB/Redis/queue endpoints).
4. Обновить README с единой командой запуска.

**Критерий готовности:** сервис поднимается полностью через compose и не зависит от локальных путей/настроек.

---

### Этап 1 — База данных и миграции (durability)
**Цель:** получить устойчивую БД и управляемую эволюцию схемы.
1. Перевести `backend/app/db.py` на PostgreSQL URL из env.
2. Инициализировать Alembic, сгенерировать миграции для текущих моделей (`backend/app/models.py`).
3. Спроектировать замену SQLite FTS5 на PostgreSQL (tsvector/GIN или pg_trgm) и выделить отдельный search‑слой.
4. Ввести миграционный процесс: локально (`alembic upgrade head`) и в CI/деплое.

**Критерий готовности:** сервис работает на Postgres, миграции воспроизводимы, SQLite больше не используется.

---

### Этап 2 — Очередь и воркеры (reliability)
**Цель:** гарантированная доставка задач и масштабируемые worker‑пулы.
1. Заменить in‑memory `TaskQueue` на Celery + RabbitMQ.
2. Сохранение статуса задач перевести в устойчивое хранилище (Redis или таблица Postgres).
3. Ввести приоритетные очереди (heavy/medium/light) и отдельные worker‑пулы.
4. Настроить retries, backoff и DLQ для критичных задач (billing/auth/webhooks).

**Критерий готовности:** фоновые задачи не теряются при рестартах, нагрузка распределяется по очередям.

---

### Этап 3 — Redis: кэш, rate‑limit, ephemeral sessions (performance & protection)
**Цель:** снять нагрузку с БД и защитить публичные эндпоинты.
1. Ввести единый слой кэша (например, `services/cache.py`) и описать key‑namespace/TTL.
2. Реализовать rate‑limit middleware (IP/User/Token buckets).
3. Вынести ephemeral sessions, одноразовые токены и throttling counters в Redis.

**Критерий готовности:** публичные эндпоинты защищены, есть метрика cache hit ratio.

---

### Этап 4 — Аутентификация и профили (identity)
**Цель:** перейти от однопользовательской модели к многопользовательской.
1. Добавить модели User/Identity/Profile.
2. Реализовать OAuth вход (Google/Yandex) с refresh‑токенами.
3. Ввести профили и базовые настройки пользователя.
4. Защитить ключевые API auth‑middleware.

**Критерий готовности:** API закрыт авторизацией, пользователи имеют профили.

---

### Этап 5 — Организации и RBAC (multi‑tenant)
**Цель:** обеспечить многопользовательскую модель и контроль доступа.
1. Ввести Organization, Membership, Role.
2. Привязать Project к Organization.
3. Централизовать авторизацию через policy‑layer.

**Критерий готовности:** проекты доступны только участникам организации с нужной ролью.

---

### Этап 6 — Биллинг и entitlements (monetization)
**Цель:** монетизация и контроль доступа к функциям.
1. Добавить модели Feature, Plan, Subscription, Entitlement.
2. Реализовать проверку entitlements в API и серверах задач.
3. Интегрировать платежный провайдер и обработку webhook‑событий.

**Критерий готовности:** платные и бесплатные фичи корректно ограничиваются тарифами.

---

### Этап 7 — Observability и SLA (operations)
**Цель:** управляемость и раннее обнаружение деградаций.
1. Добавить метрики (Prometheus) и трассировку (OpenTelemetry).
2. Ввести корреляционные ID в логи.
3. Настроить алерты по latency/error rate/queue depth.

**Критерий готовности:** есть полный мониторинг API и фоновых задач.

---

### Этап 8 — Объектное хранилище и артефакты (scaling storage)
**Цель:** устойчивое хранение больших патчей/артефактов.
1. Ввести storage‑абстракцию (локально/S3‑совместимо).
2. Перенести хранение патчей и артефактов в объектное хранилище.
3. Добавить signed‑URLs для выдачи больших данных.

**Критерий готовности:** артефакты доступны независимо от конкретного инстанса.

---

### Этап 9 — Масштабирование инфраструктуры (1M DAU readiness)
**Цель:** обеспечить устойчивость под высокой нагрузкой.
1. Kubernetes‑деплой с autoscaling (backend, workers, queue).
2. Горизонтальное масштабирование Redis/RabbitMQ/Postgres (или managed‑сервисы).
3. CDN/edge‑proxy + WAF правила для публичных эндпоинтов.
4. Регулярное нагрузочное тестирование и capacity planning.

**Критерий готовности:** сервис выдерживает рост нагрузки без деградации.

## 4) Риски и замечания
- Переход с SQLite FTS5 на Postgres требует проектирования поискового слоя и проверок актуальности индексов.
- Очередь задач критически важна для стабильности под нагрузкой, поэтому перенос `TaskQueue` обязателен до запуска SaaS.
- Реализация auth/billing меняет контракты API, потребуется versioning или миграция клиентов.

2) PostgreSQL + Alembic

4) Redis + rate‑limit

6) RBAC (организации)
7) Billing
8) Observability
9) Объектное хранилище + Kubernetes
